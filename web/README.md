# NGC WebAssembly emulator: browser application

A browser front end for the Rust/WebAssembly engine (`ngc-wasm`) that runs the unchanged **main 5.8** and **handset 65.3** firmware of a **TRITON** or **NEPTUN** release over CAN. It needs no Renode and no server-side emulation: a static page, a Web Worker and one `.wasm` file. The only network use is the optional **Load from URLs** (below), which fetches the two firmware files through a small proxy; choosing or dropping files needs no network at all. Its user interface follows the viewer of the Renode-based analysis workspace (not public): a basic, player-facing view with simulated conditions, and a closed Advanced panel with the raw inputs, outputs and diagnostics.

It is a **functional model**, not a claim of physical accuracy. The engine is new (ported from the Renode 1.17.0 behavior); results labeled `ngc-wasm/<version>` do not inherit Renode evidence. Design and contracts: [../DESIGN.md](../DESIGN.md) (sections 1, 10, 14 and 15). A hosted copy runs at <https://triton.divehub.ai>; you bring the firmware.

## Run

```sh
python3 web/build.py      # ../cargo (tools/rust or cargo on PATH) -> web/pkg/ngc_wasm.wasm (ignored by Git)
python3 web/serve.py      # http://127.0.0.1:8770, loopback only
```

Open <http://127.0.0.1:8770>. The page asks for the two original S-record files of one release, `ngc_main_5.8_<TRITON|NEPTUN>.srec` and `ngc_handset_65.3_<TRITON|NEPTUN>.srec` (file pickers or drag and drop, either order, also one drop with both files). The worker verifies them (SHA-256, record counts, span hash, vector table, board role, release). A verified file is **one compact line** in its card (a check mark, the release and board such as "TRITON main controller 5.8", the file name and size, and **Remove**); the SHA-256, the address it was loaded from and the list of checks ("9 of 9 checks passed") sit in a **closed details element** inside the card, which stays as the user left it while the options change. A failed check is listed outside it and is never folded away; a waiting card is two short lines; a wrong, damaged or swapped file is refused with the engine's message. The page names the release it recognized, and a **mixed pair** (for example the TRITON main with the NEPTUN handset) is refused with a message that says which file to remove. **Boot emulator** starts the session; **Start game** (beside it) starts the same session as the dive game ([Dive game](#dive-game-start-game-design-21)). The two firmware slots are on top; the drop zone and **Load from URLs** share one collapsible section, **Choose firmware files or load them from URLs**, which is open while a file is missing, folds away once both files are in (or remembered files are used) and opens again when a file is removed or a file is dragged over the page. Below it are **Start options**, **Remember these files** (it applies when the session boots, so it sits above the Boot button) and the Boot button; the functional-model disclaimer is at the bottom. After Boot the page opens at its top. Nothing is uploaded and the firmware is never bundled, copied into `web/` or served (see the development aid below for the one opt-in exception).

`serve.py` options: `--port N`, `--wasm FILE` (serve another module), `--quiet`, `--dev-firmware DIR` (repeatable). It serves `web/pkg/ngc_wasm.wasm` (from `build.py`) or, when that is missing, the newest release module in the cargo target directories. `build.py` options: `--target-dir`, `--debug`, `--no-build`, `--no-copy`. No dependencies beyond the Python standard library, a Rust toolchain (see the root README) and a browser.

### Load from URLs (entry screen)

Instead of choosing files, the entry screen can **fetch the two S-record files from addresses**. The page is only a client: the sources (`api.multi3s.com` and the Wayback Machine) send no CORS headers, so a page cannot read them directly, and the firmware is never mirrored. The request goes to a small proxy (`../deploy/api/firmware.mjs`, a Vercel Function hosted on its own address, separate from the static site; see [../deploy/README.md](../deploy/README.md)) that fetches the one named file on demand, keeps nothing and caches nothing. Where the proxy is is a **build-time setting** (`config.js`, below); without one, the form says that loading from URLs is not configured yet and everything else works.

* **Fields.** Two address fields (main, handset; either may stay empty), prefilled with archived TRITON addresses (nothing is fetched until **Load from URLs** is pressed), a progress bar per file, **Cancel** and a 45 s timeout. It is a real form (Enter submits), keyboard accessible, laid out for phones and themed light and dark. Pasting addresses never starts anything: `?main-url=<address>&handset-url=<address>` only pre-fills the fields, and only the button fetches.
* **Accepted addresses** (`firmware-url.js`, the page-side copy of the proxy's allowlist): `https://api.multi3s.com/static/NAME.srec` and `https://web.archive.org/web/<14-digit timestamp>[id_]/https://api.multi3s.com/static/NAME.srec`, with `NAME` 1 to 64 of `A-Za-z0-9_-`. Anything else (other hosts, ports, user names, query strings, fragments, `http:`, IP addresses, percent-encoding, other paths) is refused with a reason before any request. The Wayback form is normalized to the raw `<timestamp>id_` form and the field shows the exact address that will be requested; after the fetch it shows the address the proxy finally used (after redirects).
* **Which proxy.** The one the site was built with: `config.js` exports `FIRMWARE_PROXY_URL` (`null` in the committed default; the Pages build generates it from the repository variable of that name, see [../deploy/README.md](../deploy/README.md)), and the build adds the proxy's origin to `connect-src` of the page's Content-Security-Policy. When it is `null` there is no proxy: the address fields are hidden and the page says "Loading from URLs is not configured yet"; it **never falls back to a same-origin `/api/firmware`**. A page on `localhost` / `127.0.0.1` (`serve.py`) can in addition use a loopback dev proxy named by `?firmware-proxy=http://127.0.0.1:<port>/api/firmware` (only honored on a loopback page and only for `http://127.0.0.1` / `http://localhost` addresses with exactly that path; otherwise ignored with a note), which wins over the configured proxy. The page names the proxy in use under the form. For a local test without Vercel run `node deploy/dev-proxy.mjs`.
* **Verification.** The fetched bytes take exactly the path of a dropped file: the worker's `inspect` (SHA-256, record counts, vector table, board role, release), slot assignment by content (a handset image typed into the main field still lands in the handset slot, and the field says so) and the mixed-release refusal (with the file's SHA-256). **Remember these files** applies unchanged. Unknown firmware, a mixed pair, a refused SREC and every fetch failure (address not allowed, proxy unreachable, proxy does not serve this page, source HTTP status, too large, not an SREC, timeout, canceled) are shown on the field with a message that says what to do.
* **Privacy.** The proxy host sees the address you enter and the request (the proxy host's own request log, for example Vercel's, keeps the path and query for a limited time); the page sends nothing else and the files are never uploaded anywhere.

### Custom firmware builds (entry screen, "Use custom firmware builds"; DESIGN 20)

An explicit checkbox at the top of the entry screen, **off by default**, switches the page from the TRITON / NEPTUN loading to **custom (native) builds**: the original slots, the release line, the drop zone and **Load from URLs** are replaced by one card per board.

* **One `.srec` per board.** The Main and the Handset card each have a file chooser (`accept=".srec"`) and take a file dropped **onto that card**; the card decides the role (both native builds share a reset vector, so the content cannot). A drop outside the cards does nothing and says where to drop; a second file on one card is ignored with a note; a file that is not `.srec` is refused on the card. There is **no URL loading** in custom mode and no release verification.
* **The structural report** of `ngc_firmware_inspect_custom` (S-record syntax, address range, span, vector table, initial SP, reset vector, entry point) is shown per card in the page's compact style: a verified card is one line (check mark, "Main (custom build)", file name and size, **Remove**) and a closed details element holds the checks, the **SREC and binary SHA-256**, the **span**, the **initial SP** and the **reset PC** (and the entry address). A refused file keeps its failed checks (and the engine's message, when no check says it) in view, with **Dismiss** and **Choose another file…**.
* **Booting** sends `custom: true` with the `boot` request; the worker keeps the custom files apart from the original ones (`runtime.custom`), gives the engine `ngc_set_custom_firmware` and runs the one shared **custom profile**. The session title, the header (`Custom build · main + handset · …`) and the window title say **Custom build**. A cold boot the engine refuses (it must detect the build's standby request) shows the engine's message on the entry screen, or under Advanced for **Cold boot**.
* **No original-firmware claims.** Fields the engine reads from the original firmware's RAM (batteries ready, decompression state, terminal-handler detection) show **Unknown** with the engine's reason; `decoHealth` never warns while unknown; the battery-wizard note, the cold-boot calibration hint and "Release: TRITON …" lines are hidden or replaced. The session information says that release verification was skipped and that the handset wake fixture writes only `PWR.SR1` and `RCC.CSR`.
* **Profiles.** `custom` is one OPFS (and IndexedDB) area shared by every custom build, separate from `profile` (TRITON) and `profile-neptun-…`. **Reset profile** (Advanced, or the entry-screen note) clears only the area of the session or mode in use; the user resets it before loading a build that stores its data differently. **Remember these files** applies with the same semantics (on by default, OPFS only) to a pair of its own in `firmware-custom`, offered by its own banner in custom mode and never mixed with the remembered original pair. Switching between the modes only changes which files, profile and banner the screen shows; the files of the two modes, their profiles and the UART view of the previous session are never shared (a new session starts with an empty UART console and output rows, and without the earlier session's save time).
* **Development aid.** `serve.py --dev-firmware DIR` with `/?dev-firmware=custom` loads the TRITON files into the custom slots (same file names as the original route, through the structural checks only).

### CPU faults (every release)

The state carries `faults: {main, handset}`, each `{cfsr, hfsr, lockup}` (`lockup` is `null` or the engine's reason). The basic view shows **a short line per board only when a register is nonzero or the core is locked up** (a strip under the alert indicators); Advanced > Execution and model details lists both boards ("Main faults", "Handset faults"; "—" without the report, and for the main board of a handset-only run). `faults.js` reads the report.

### Start options (entry screen, "Start options")

System (dual / handset only), boot (handset wake / cold; choosing cold shows a hint that the firmware clears the oxygen calibration on that wake cause), board-ID ADC sample (default 400), the **start at the surface** fixture (`start-surface`, on by default, named in the state; the EEPROM factory image has no option, see below), the **main I2C idle-high fixture** (on by default: the main board's PB6/PB7/PB10/PB11 are driven high before the firmware runs, standing for external pull-ups; it is an idle-line fixture, not electrical I2C modeling, and leaving PB6/PB7 low changes the start-up ordering of settings loading and HUD initialization), simultaneous CPU start, start paused, and the exact idle fast-forward (host speed only; results are identical with it on or off). Every session creation also passes a random `historyNonce`, so the output-history epochs of two launches never coincide.

### Decompression warnings and fixtures

The original TRITON firmware loads NaN tissues from a profile that was booted once and restarted (it saves its tissues only on power-down), and its ppO2 is NaN with uncalibrated oxygen cells; either keeps the no-decompression limit at 99. The engine reports this read-only (`decoHealth`, DESIGN section 17) and the page shows it:

* **Warnings** (a strip between the alert indicators and the LCD, only for a proven bad state; `unknown` never warns, which is what NEPTUN, a handset-only run and an older engine give): "Decompression state invalid: this profile's stored tissues are blank. Reset the profile (Advanced → Profile and evidence → Reset profile) to start with an initialized EEPROM." (an older profile that never saved its tissues; a new EEPROM is created with valid ones, and an existing EEPROM is never repaired). Uncalibrated oxygen cells are not shown as a warning; the report keeps them. Advanced > Loaded firmware and session lists the report and what each fixture did at the last start.
* **Start options** (checked by default, passed as `startAtSurface`): *Start at the surface* (every board creation starts both pressure inputs at the surface pressure plus the sensor offsets, a new session also with the default oxygen cells). It is an emulator fixture, named in the state and in captures. The EEPROM factory image has **no** start option: when the engine creates a new EEPROM (a profile without `eeprom.bin`, or an entirely erased one) it writes the image once (serial 1, oxygen-toxicity values, surface tissues, no-fly time 0, derived from the firmware; `docs/eeprom.md`), and an existing EEPROM is never touched; the session information says which happened.
* **After a Restart** the form follows the engine: when a Restart, Cold, Wake or serial change returned the pressure to the surface, the depth slider shows 0 m and the raw fields show the new readings; the oxygen cells keep their values (only a new session, which includes a profile import or reset, resets them). When it left the sensors as they were, the form and any raw draft stay as they are.
* **Surface pressure** is the page's own setting (`inputs.json` does not hold it): the basic view's field is remembered in this browser (`localStorage`, `ngc-wasm.surface-pressure`), is passed as `surfacePressureMbar` when a session starts and goes with every Restart, Cold, Wake and serial change.
* **Cold boot**: the Advanced Cold boot button carries a hint that the firmware clears the oxygen calibration (flags `0x09` back to `0x01`) and the calibration has to be repeated.

### The clock of a new profile (DESIGN 23)

A new profile (also after Reset profile, an import without `rtc-state.json` or the game's Reset all) starts both RTC calendars at the engine's 2020-01-01 default: the page sends no time and the engine never reads a host clock. The saved RTC checkpoint then keeps the device time across sessions; it advances in virtual time only (paused or closed means frozen, and 4× play runs it ahead of the wall clock), so the device time is consistent but is not the local time. Advanced > Loaded firmware and session shows where each board's calendar came from ("Clock (...): no saved checkpoint (fresh RTC)", or the restored boards). The engine builds of 2026-10-10 started a new profile from the browser's local time (`initialLocalTime`) instead; that was removed the same day (user decision, DESIGN 23), and the profiles saved meanwhile, whose `rtc-state.json` names the provenance `host-local-time`, still load like any other.

### Releases

The engine identifies the release of each image (`release: {id, label}` in the inspection report; `TRITON-5.8-65.3` and `NEPTUN-5.8-65.3` are known). The page shows it on the slots, the header and the window title, and the session information. **Each release has its own saved profile**: TRITON keeps the original storage location (`ngc-wasm/profile/`), every other release gets a directory of its own (NEPTUN: `ngc-wasm/profile-neptun-5_8-65_3/`; in IndexedDB the equivalent object store), so EEPROM, log flash, RTC checkpoint, sensor inputs and LED labels are never shared between releases. Export, import, Reset profile and the "saved profile" notice on the entry screen act on the profile of the release in use. The remembered-firmware option keeps one pair at a time (remembering another release replaces it) and records its release.

### Remember the files (on by default)

**Remember these files in this browser** is checked by default: booting stores the two verified SRECs in the origin-private file system (OPFS; not available in IndexedDB). On the next visit they are verified again and used automatically; the banner under the slots then says so and offers **Forget them**, and **Use the remembered files** appears only when a slot was removed or filled by another file. Uncheck the box before booting to be asked for the files each time; **Forget them** removes the stored pair (and unticks the box). Where the browser has no OPFS the box is disabled and unchecked with an explanation, and booting works as before. The files are only ever read by this origin; nothing leaves the browser.

## The page

### Basic view (player-facing)

| Area | Behavior |
| --- | --- |
| Status strip | **Vibrator**, **Red LED** (HUD 3) and **White LED** (HUD 2) above the LCD: On, Off, Unknown or **Pulse** (a replayed flash). These show the *commanded* outputs of the firmware; physical light output and motor current are unverified. |
| LCD | Canvas, nearest-neighbor scaling (whole device-pixel multiples when they fill at least 85 % of the panel, otherwise fit; switchable), 4:3 panel, placeholder until the firmware turns the panel on. Frames arrive only when the visible pixels change (at most 60 per second, transferable buffers). |
| Buttons | Up / Down / Confirm and keyboard arrows / Enter (a held key is one press; the ↑ ↓ keys belong to the handset only, wherever the focus is, and never scroll the page or change a field; Enter yields to fields, selects, links, buttons and disclosure summaries, so opening Advanced or a variations section from the keyboard never confirms in the guest), and taps on the LCD (upper third Up, middle third Confirm, lower third Down; a hint under the buttons says so). Physical pulses through TIM3 capture; Confirm uses the two staggered 204.8 ms pulses (50 virtual ms apart) of the runner. |
| Execution | Pause / Resume and Restart boards side by side (on a phone as well), **Speed** (0.25x to 4x or unpaced), virtual time. Advance N s is under Advanced. |
| Simulated conditions | **Oxygen**: a 0 to 100 mV base plus three signed cell offsets. **Pressure / depth**: surface pressure (mbar), a 0 to 110 m depth and Fresh 1000 / Salt 1025 / EN13319 1020 kg/m^3 water, `mbar = surface + density x 9.80665 x depth / 100 + offset`, two signed sensor offsets. **Temperature**: a -4 to 40 C base plus two signed offsets. Each **Sensor variations** section starts collapsed. The sensors are numbered as the firmware numbers them (below). |

**Sensor numbering.** The page numbers the two MS5837 sensors as the firmware does, which is the reverse of the engine's input keys (the Renode model names, kept unchanged so `inputs.json` and the command-line scripts stay compatible): **sensor 1 is the device on I2C2** (`pressure2Mbar`, `temperature2C`) and **sensor 2 the device on I2C1** (`pressure1Mbar`, `temperature1C`). "Sensor 1 offset", the previews `P1`/`P2` and `T1`/`T2`, the "Pressure sensor 1" in a rejection message and the Advanced raw fields ("Pressure sensor 1 (I2C2, absolute mbar)", and so on, sensor 1 listed first) all follow it; the raw fields keep the engine names as their form field names, and a short note in Advanced states the mapping once. `sensors.js` holds the tables (`PRESSURE_KEYS`, `TEMPERATURE_KEYS`, `SENSOR_BUSES`). The numbering follows a user's reading of the handset display; it is a functional mapping, not a statement about the physical sensors.

Basic edits apply immediately (no Apply button). The calculated seven raw model inputs fill the raw fields of the Advanced panel and go out as one `inputs` action. An invalid sum (the raw ranges are oxygen 0 to 250 mV, pressure 100 to 30 000 mbar, temperature -20 to 85 C) or an incomplete number (a blank field is not zero) shows **Not applied** and sends nothing; readings are never clipped (a sum that misses a limit only by floating-point rounding is snapped to it). Every UI action goes through one queue: actions run one at a time in order, adjacent *pending* basic updates coalesce to the newest, and an explicit raw **Apply inputs** is an ordered snapshot that keeps its place. Revision counters keep stale replies from overwriting newer edits (a reply rebases the basic controls only if no basic edit and no newer raw sensor edit happened since, and refreshes the raw fields only if no raw edit did; status broadcasts never touch the fields). The status reads **Applying...**, **Inputs applied** or **Raw edits pending**. Bases and offsets are derived from the current raw inputs whenever a session starts or the profile is replaced, and when a Restart, Cold, Wake or serial change returned the sensor inputs to the surface (the start-at-the-surface fixture, below); nothing is stored separately, and the raw inputs persist in the profile. These controls are local input fixtures, not a claim about physical sensor accuracy; firmware filtering and stored calibration still determine what the handset shows.

### Advanced · raw inputs, outputs and diagnostics (closed initially)

Raw sensor fields with **Apply inputs** (drafts until applied; the engine's ranges and messages unchanged, any decimal accepted; the two pressure and the two temperature fields name their sensor and bus, see "Sensor numbering" above; a **fresh profile starts with both batteries at 4100 mV**, a saved profile keeps its stored values, and the page's own default only shows until the engine's values arrive; the firmware compares the voltage with the battery type chosen in its wizard: 4100 mV suits Li-Ion 3.7V-18650, while after choosing Alkaline about 1500 mV is needed, otherwise the next start shows "Change battery" and the unit goes to standby), then a **Boards, CAN link and serial number** group: CAN connect / disconnect and Drop ID, Cold boot, Wake system, the emulated serial number (0 to 999 999 999) and storage summaries (the evidence zip is saved only from **Profile and evidence**), the **raw hardware outputs** (Drive, Replay and history per output, HUD color selectors Unknown / Red / White, LCD backlight), the read-only **UART console** (five channels, Text / Hex; retained 16 KiB tails, shown as at most 65 536 characters; the worker sends the bytes only while the console is on screen; the channel select is written only when the channel list changes, because a browser rebuilds or closes an open dropdown whenever its options are touched, even with identical text, so the page never rewrites them on its 5 Hz state updates, and the console text only when it differs), **Advance and pacing** (**Advance N s**: 0.01 to 20, run in 0.5 s chunks with progress and Cancel; background-tab policy; real-time factor and engine capacity), execution and model details (PCs, batteries ready, mode, LCD summary), **Profile and evidence** (export / import / reset, evidence zip) and **Loaded firmware and session** (release, files with hashes, start options, fixtures, clock persistence provenance, executed instructions with the idle fast-forward share, machine resets).

### Replay pulses (on by default, Advanced > Raw hardware outputs)

The engine keeps bounded histories of the commanded drive per output (`activity`, and `pwmActivity` for the vibrator; DESIGN 15.3a): HUD commands sampled every 50 virtual ms, the vibrator's PB15 enable changes exactly and its gated motor command sampled every 20 virtual ms. A short pulse can fall between two status updates. With replay on, the current command stays steady while it is On; when it is Off, activations newly observed since the last update queue wall-clock flashes, **150 ms on and 100 ms gap, at most 12 per output**. The first observation (initial load, reconnect, an Unknown drive) is only a baseline and never replays; a new `outputHistoryEpoch` (or restart generation), missing history, a count regression, a changed overlap or a sequence gap clears the queue (the gap is reported as "history events unavailable"). A hidden tab clears replay and never plays a stale catch-up. Separate **Drive** and **Replay** labels keep the current command, the configured duty and the virtual-time evidence apart from the animation. **Replay is a visibility aid, not firmware timing**: a flash can outlast the command that caused it, and a command shorter than the sampling period can be missed. Turn it off to inspect the current drive alone. An engine without histories simply shows the drive.

## Dive game (Start game; DESIGN 21)

**Start game** sits beside **Boot emulator** on the entry screen. It starts the same session (the same verified firmware, original or custom, the same profile and the same start options) and shows it as a game instead of the emulator view: you dive in the water scene, the depth and the gas in the loop become the emulated pressure and oxygen-cell inputs, and you operate the handset through its own display. It needs both boards, because the main board owns the sensors: with "Handset only" selected the button is off and the entry screen says why. **Desktop only** for now: the layout is designed for windows of about 1000 px and wider, and has no phone layout. There is no switch between the game and the emulator view; **Quit** (in the header, which stays in view; see the table) closes the session the way the emulator view's close does (the profile is saved) and returns to the entry screen, where **Boot emulator** works as before. The sticky header holds, from left to right, the release, one **clock chip** (the virtual time, the play speed and the run state: its dot always has the run state's color, and its word shows unless the emulator is simply running; the chip replaced the badge that sat beside a hero heading, which is gone to save vertical space, and its ids `game-virtual-time`, `game-header-speed` and `game-run-state` are unchanged), **Reset all**, **Quit**, the **sound** button and, at the far right, the **?** controls button; at 1280 and 1440 px wide nothing overlaps or wraps. Text that informs is at least 10 px (only the bezel's print is smaller, and it is hidden from screen readers), the MAV buttons' accessible names begin with their visible names ("Oxygen MAV, hold to inject"), and the game's workspace is the page's main landmark while it is shown (the page's own `<main>` is hidden then, so there is never a second one in view).

| What | Drives what |
| --- | --- |
| **Clock** | The emulator's virtual time only (the `virtualTime` of every published state; no local clock). Depth, gas, the dive profile and the header clock all follow it. **Pause / 1× / 2× / 4× / Uncapped** (the play control in the water) set the emulator's pacing: the engine's pause and resume, the `speed` request, and Uncapped is the unpaced engine. **Space** pauses and resumes. Start paused (a start option) starts paused. A hidden tab follows the worker's pacing rules (backlog is skipped, never replayed); the game lets go of the water and the valves. |
| **Depth to pressure** | Both pressure inputs get the session's surface pressure (the page's setting, 1013.25 mbar by default) plus EN13319 water (1020 kg/m³, 9.80665 m/s²) times the depth, through `sensors.js` and the page's sensor numbering (`PRESSURE_KEYS`; both sensors get the same value). The inputs go out through the `inputs` action, **coalesced and serialized** (the newest wins, one request in flight, at most four per wall second, none while the values are unchanged). The temperature keeps the emulator's setting. The game never writes guest RAM. |
| **Gas to oxygen cells** | The loop model (`game-gas.js`: two 2 L counterlungs, perfectly mixed, 4 L of ambient volume, MAV, ADV and venting in surface-equivalent liters) gives the oxygen fraction; ppO₂ is that fraction times the ambient pressure sent to the firmware. Each cell voltage is ppO₂ times its sensitivity (see the fixture below). The oxygen cells panel shows the **voltages sent to the firmware** and, labeled as the **simulated truth**, the loop ppO₂; what the firmware makes of the voltages (after you calibrate) is on the handset. Selecting a **diluent** switches the supply only, as turning to another cylinder would: the counterlungs keep their gas, and the new mix enters with the next ADV addition (a descent) or diluent MAV. The diluent in the firmware is the diver's job on the handset. |
| **Wrist unit** | The firmware's LCD frame in the bezel (the emulator's renderer). The bezel's **Up** and **Down** keys press the handset's Up and Down (the same pin pulses as the emulator view); tapping the display is **Up** in the upper third, **Confirm** in the middle third and **Down** in the lower third. **↑ ↓** press Up and Down wherever the focus is (they never scroll the page or change a field); **Enter** confirms while the handset has the keyboard focus (click it, or Tab to it; a ring shows it). No key and no bezel button ever moves the diver. The **Vibrator**, **Red HUD LED** (HUD 3) and **White HUD LED** (HUD 2) indicators show the firmware's commanded outputs with the pulse replay of the emulator view (`replay.js`; they are not controls). |
| **Dive profile** | The chart records the dive only, like a dive computer. It starts when the diver first leaves the surface (the depth goes above 0 m): the profile and its "elapsed" time begin at 0:00 at that moment, so the time on the boat or floating at the surface before it is not recorded and there is no flat line at the start. Reaching the surface again ends the dive: the final surface point is included and nothing more is recorded while the diver is at the surface. An integration step that reaches the surface or the 110 m floor is split at the moment of arrival (the motion up to it, the rest of the step at rest), so the dive time, the profile and the gas are the same whether a state brings 3 s or thirty states bring 0.1 s. A new descent starts a new profile, so the chart always shows the current or the last dive; the maximum depth (the meta line and the gauge marker) is per dive as well. Before the first descent, and after Reset all or in a new session, the chart is empty and says "No dive yet". Long dives still thin their samples (at most 2 401 points, the whole time span kept). The ADV and vent indicators use the session time, which keeps counting. (`GameSim.profile`, `diveTime`, `diving` in `game-logic.js`.) |
| **Reset all** | The header button (replacing the older Reset dive). After a confirmation ("Reset all? This erases the dive computer's memory: settings, calibration, logbook and clock. Both boards restart as new, and the diver returns to the boat.") it **closes the session without saving**, **clears the whole profile area of the release** (EEPROM, log flash, RTC checkpoint, inputs and LED colors, plus the game's oxygen-cell deviations, through the worker request the start screen's "Reset the saved profile" uses) and **starts a new game session** on the same firmware with the same start options: the EEPROM factory image is written again (DESIGN 18), both clocks start at the engine's 2020-01-01 default (above), the diver is on the boat with a fresh Air loop at 1×, the virtual clock starts from zero and the profile chart is empty ("No dive yet"). The header says "Resetting…" and Reset all and Quit are off while it runs (the keyboard belongs to the confirmation; while the session is replaced no key reaches the game, and the arrow keys and Space still do not scroll the page). **The water view (DESIGN 22): one depth story, from the boat to the dark.** The water panel is a side view with a following camera at a **fixed 30 m window** (it no longer zooms out with the maximum depth). The camera follows the diver's virtual depth with a **dead zone in the middle third** of the panel, smoothly (critically damped over about a third of a second, exact for any frame rate), so it keeps up at 4× and Uncapped, and it clamps at the top (6 m of sky, the surface and the boat in view) and at the 110 m seabed (some sand in view). The drag gesture is unchanged (screen-space displacement from the press point); its ring, tether and contact stay in screen space. What makes the motion visible while the diver stays near the middle:

- **World-anchored depth lines** every 5 m, labeled every 10 m; **marine snow** drifting through the water in three depths (the far one moves slower than the camera, the near one faster: parallax), so it streams up on a descent and down on an ascent; **light rays and distant fish shapes** that move at 45% of the camera's speed and fade out with depth.
- **Light by depth.** The water color follows depth: bright turquoise at the surface, deep blue around 30 to 40 m, near black by 100 m (one color table, `WATER_STOPS` in `game-logic.js`, drives the panel's gradient and the gauge).
- **Depth gauge.** A slim strip at the panel's left edge shows the whole 0 to 110 m range in the water's colors, with the 30 m window the camera shows, the maximum depth (gold) and the diver. (The profile chart still shows the whole dive.)
- **Boat and entry.** A session starts with the diver sitting on the stern of a small boat that bobs at the surface. The **first descent** plays a short back roll off the boat with a splash (spray, two ripples, foam; about 1.1 s of wall time). It is purely visual: the depth and the emulator inputs follow the simulation from the first moment, the entry only draws the diver. **Reset all** starts a new session with the diver on the boat, so the next descent plays the entry again; surfacing later leaves the diver floating at the surface beside the boat, with no second entry.
- **Vent bubbles (CCR-accurate).** A closed loop makes no bubbles. Bubbles rise from the diver only while the loop vents, and in proportion to the vented gas: the loop model's own `vent` (an ascent expanding the loop, or a MAV giving more than the loop volume takes), exposed read-only by `GameSim.takeVented()` in surface-equivalent liters (one bubble stands for 0.025 SL). Holding depth or descending makes none; there are none on the boat or at the surface (they vanish there); they grow as they rise (Boyle) and rise on the dive's clock, so at 4× they rise four times as fast on the screen, like the diver. The gas physics and everything sent to the emulator are untouched.
- **The dark zone from 40 m.** At 40 m the diver's torch switches on (off again only above 39 m, so it does not flicker at the boundary): a soft light cone in front of the diver that also lights the marine snow inside it, and the speedometer dial glows softly, like a luminous dial in the dark.
- **Pause and motion preferences.** Paused: the camera holds, the drift, the bobbing, the splash and the bubbles stop. With **`prefers-reduced-motion`** there is no drift, parallax, bobbing, wave animation or entry animation (the diver simply appears in the water), the torch comes on without a fade and the camera moves without easing; the vent bubbles stay, because they carry information (the vent state), but without their sway.

Rendering: the three tall layers (water gradient, far layer, world) are moved by the camera with one compositor transform each; one canvas above them draws the marine snow, bubbles, splash and torch; the diver and the boat are SVG. It runs on `requestAnimationFrame` only while the game screen is shown (it stops on Quit), advances by the wall time between frames (at most 0.1 s, so a hidden tab does not make it jump), and writes to the page only what changed. In the browser check the frame callback cost about 0.14 ms on average (0.3 ms at most) with the torch on; it only reads the simulation and never feeds back into it. The decorative layers are `aria-hidden`; the water's label, the speedometer's `meter` role and the diver's label are as before.

**The oxygen-cell fixture (a labeled game fixture, not a physical cell).** Each cell reads **12 mV in air at the surface plus its own random deviation, uniform within ±1.0 mV** (11.0 to 13.0 mV at a loop ppO₂ of 0.2128 bar), linear in ppO₂ and without drift. The deviations are drawn once per profile and kept in this browser's page settings (`localStorage`, `ngc-wasm.game-cells.<profile area>`, for example `profile`, `profile-neptun-5_8-65_3` or `custom`), so a calibration made through the firmware menu (Menu → Calibration → Air → Auto → Start → Save) stays valid across sessions, like a real cell. **Reset all** (in the game's header), **Reset profile** (the start screen's note or Advanced) forget the area's deviations; the next game session draws new ones. The three values are listed under **Game assumptions**. The firmware accepts the uncalibrated cells (11 to 13 mV in air) for the calibration. A very high ppO₂ saturates a cell at the engine's 250 mV input limit instead of being refused.

**Simulated cell faults (DESIGN 26).** Each cell reading in the **Oxygen cells** panel is a button ("Simulate a cell fault"). A click, or Enter with it focused, opens a small menu anchored under that cell, built like the controls guide and the sound popover (not a modal; opening it lets go of the water and the valves; Escape, the cell again, a click outside or the focus leaving close it). It lists six states as radio items, the current one checked; choosing one applies it at once and closes the menu, so the diver can jump straight to a state without passing through others (a short on the way back to normal would send 0 mV). While it is open the keyboard is the menu's: ↑ and ↓ move between the items (Home and End to the ends), Enter or Space chooses, Escape closes it, and no game key (the handset arrows, W / S, O / D, Space's pause) reaches the game. The focus goes into the menu (on the checked item) and back to the cell when it closes. A choice sends the inputs promptly, through the same throttled sender as a diluent switch (at most four sends per wall second).

| State | What the game sends for that cell | Shown on the cell |
| --- | --- | --- |
| **Normal** | The fixture value above (its ±1 mV deviation kept); switching back restores it at once. | As before: no ring, no badge. |

## Pacing

The engine never reads a clock; `worker.js` / `runtime.js` pace it against `performance.now()`:

* the engine runs in slices of **10 virtual ms** (`Session::run_for`; the result is a pure function of the firmware, configuration and inputs, so slicing never changes it);
* every timer tick computes `target = epochVirtual + elapsedWall * speed` and runs slices until it has caught up or used its **10 ms wall budget**; it then yields so UI messages (button presses, actions) are handled between slices, and sleeps until the next slice is due. Zero-delay yields use a `MessageChannel` (no 4 ms timer clamp);
* a backlog above **250 virtual ms** is forgotten (never spiral) and reported as "backlog skipped"; Pause / Resume / speed changes / returning to a hidden tab restart the reference;
* **real-time factor** = virtual seconds per wall second over the last 2 s (about 1.00 when keeping up); **engine capacity** = virtual seconds per second of engine execution (the speed the engine could sustain; conservative while paced because every slice starts cold). The badge says "not keeping up" when the factor falls behind or backlog was skipped. The measured factor is also written to the state document (`realtimeFactor`, captured in `state.json`);
* state is published at 5 Hz (1 Hz while the page is hidden), frames only when they change (at most 60 per second, at most 1 per second while hidden), with back-pressure (at most three frames in flight).

**Hidden tabs.** Browsers throttle or deprioritize background pages (timers, even workers; Safari and Firefox more than Chromium). Because virtual time is deterministic, this only slows wall-clock progress. Default policy "Keep running": the loop continues at whatever rate the browser allows, skips backlog above 250 ms instead of burning through it, and sends at most one LCD frame per second (a fresh frame goes out at once on return). The browser's visibility flag is only a hint: embedded panes and occluded windows report "hidden" while the page is looked at, so a hidden page must still show its picture; an earlier version sent nothing to a hidden page and the first session after a page load stayed black until an action forced a frame. Alternative "Suspend until it is visible again" stops the loop without touching the session (the badge says "suspended"). In both cases the profile is saved when the page is hidden.

## Persistence

The worker keeps the profile of the running release in OPFS (`ngc-wasm/profile/` for TRITON, `ngc-wasm/profile-<release>/` for the others, `ngc-wasm/custom/` for every custom build), falling back to IndexedDB, then to memory with a visible warning (the page's own notices, like this one, stay in the error box on the start screen and in every session until dismissed; the notices and action errors of a session, such as the profile lock, go with it when it closes). It is written about 2 s after storage changes (`take_profile_changes`), as a full export with a fresh RTC checkpoint every 15 s, when the page is hidden or closing (`visibilitychange`, `pagehide`: closing the tab within a few seconds can lose that much clock progress; EEPROM and log flash are saved within about 2 s), on Restart / Cold / Wake / serial and when the session is closed (the runner's close semantics). A Web Lock (`ngc-wasm-profile`) keeps two tabs from writing a profile: the second tab starts from an empty profile and does not save. An invalid stored profile is never silently erased: boot reports the engine's message and offers "Erase the saved profile and boot" or "Boot without the saved profile (nothing is saved)".

The calendar advances in **virtual time only**: it stands still while the emulator is paused or closed (AGENTS.md, calendar retention). EEPROM offset 0 (the emulated serial) is synthetic storage; it never identifies a physical unit.

Bytes go through `ngc_alloc` / `ngc_free`; text and binary results through the output buffer (`ngc_output_ptr` / `ngc_output_len`) or the parts list (`ngc_part_*`). Custom builds: `ngc_firmware_inspect_custom` (structural report, no role, no release) and `ngc_set_custom_firmware` (role 0 main, 1 handset); `engine.js` offers `supportsCustom`, and an older module's missing exports make the page disable the custom choice with an explanation. A Rust panic is recorded (`ngc_panic_ptr/len`) and reaches the page as a "stopped after an internal error" notice. The benchmark half (`ngc_create`, `ngc_run_for`, `ngc_fingerprint`, ...) is independent of the session.

## Development aid

`serve.py --dev-firmware DIR` (off by default; DIR is a release directory such as `firmware/TRITON-5.8-65.3`; repeat it for several release directories) additionally serves the original SREC files of `DIR` (exactly the four known TRITON / NEPTUN names) at `/dev-firmware/<name>`, and the page loads them when opened as `http://127.0.0.1:8770/?dev-firmware` (TRITON) or `/?dev-firmware=neptun`, as if chosen by hand (`/?dev-firmware=mixed` offers a TRITON handset with a NEPTUN main file, to see the refusal). It exists for automated browser checks, where a script cannot operate the native file chooser. `/?dev-firmware=custom` loads the same two TRITON files into the **custom** slots (and switches the page to custom mode), to check the custom flow without the file chooser. Without the flag the route does not exist.

## Browser support and limits

Engine speed depends on the exact idle-loop fast-forward. With the engine build of 2026-10-08 the NEPTUN *main* image's idle loop is not recognized by it (0 % of the main board's instructions are skipped, against 98 % for TRITON), so a NEPTUN session ran at about 1.4x real time in V8 on the reference machine (TRITON: 9x boot, 20x steady) and below 1x in a busy browser; the badge then says "not keeping up". This is an engine matter, not a page setting.

Needs module workers, WebAssembly, OPFS (or IndexedDB), Web Locks and canvas: current Chrome, Edge, Safari and Firefox. No `SharedArrayBuffer` and no cross-origin isolation are required. Safari and Firefox were not exercised here (design review only); the in-browser checks were made in Chromium. Profile import of DEFLATE-compressed zips needs `DecompressionStream`; stored archives always work.
